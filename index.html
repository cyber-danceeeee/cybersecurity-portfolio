05 / Learning journey

Progress means explaining the failure, not hiding it.

Reflection · approximately 500 words

My progress in WQE7001 has been less about collecting tools and more about learning to use them with a clear scope, a defensible method, and evidence that another person can follow. Two topics made that shift especially visible: virtual lab design and network service enumeration.

Building an isolated virtual lab taught me that security work begins before a testing tool is opened. I had to think about trust boundaries, network modes, snapshots, and the difference between giving a guest internet access and exposing a deliberately vulnerable machine to the physical network. Separating a management/update path from a host-only testing segment made the architecture easier to reason about. The main lesson was that safety controls should be visible and testable: a diagram, a checklist, and a rollback point are stronger than simply assuming a lab is isolated.

The service-enumeration exercise then connected networking theory to observable behaviour. I started a web service bound only to 127.0.0.1 and used a narrow Nmap scan against two explicitly selected ports. The results showed the difference between an open port, where a process accepted a connection, and a closed port, where the host responded but nothing was listening. Service detection also showed why scan output is a hypothesis rather than a final vulnerability finding. A banner can guide investigation, but it needs verification and context before it supports a security conclusion.

One thing went wrong during the lab: my first service check failed because the test server was not ready when the scan began. I diagnosed it by checking the process, confirming the bind address, and testing the port locally before repeating the scan. Adding a readiness check and a cleanup trap to the reproduction script fixed the immediate problem and made the procedure safer. That experience reinforced a useful troubleshooting sequence: verify the simplest assumptions, isolate one layer at a time, and record the change that resolves the fault.

Packet analysis remains challenging. I can apply basic Wireshark display filters, but interpreting a long capture and distinguishing normal variation from suspicious behaviour still takes me too long. The difficult part is not finding individual packets; it is building a reliable narrative across DNS, transport, and application-layer events without jumping to conclusions.

My concrete improvement goal is to complete four documented packet-analysis exercises by 31 March 2027. Each exercise will use a legal practice capture, state a question before analysis, preserve the filters used, and end with a short evidence-based conclusion. I will measure progress with a checklist in this repository and ask a peer to reproduce at least one analysis from my notes. Success means all four reports are complete and the reviewed report can be followed without additional explanation.
